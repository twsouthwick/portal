# Build and Delivery Specifications

These EARS specifications distinguish observed behavior (`[x]`) from
specified behavior not yet fully verified (`[ ]`). Approved release
requirements now have workflow, implementation, and local-test coverage;
hosted publication and signing runs remain unverified.

- [x] **DELIVERY-001** When the web project is built, it shall type-check and bundle the frontend through its npm build integration. Evidence: `Portal.Web/Portal.Web.csproj:22-24`, `Portal.Web/package.json:1-15`.
- [x] **DELIVERY-002** When a pull request or configured branch/tag push runs the main workflow, CI shall build and test the .NET solution, validate container packaging, and lint the Helm chart. Evidence: `.github/workflows/build.yaml:1-11,164-224`.
- [x] **DELIVERY-003** When the main workflow runs on supported desktop runners, it shall build and smoke-test the configured Linux and Windows native-client targets. Evidence: `.github/workflows/build.yaml:14-162`.
- [x] **DELIVERY-004** When the Android workflow runs, it shall build an x86_64 debug APK, install it in an emulator, and run smoke/UI checks. Evidence: `.github/workflows/android.yaml:1-91`.
- [x] **DELIVERY-005** When a successful push meets the workflow's publishing conditions, CI shall publish the versioned container image and Helm chart to GHCR. Evidence: `.github/workflows/build.yaml:223-300`.
- [x] **DELIVERY-006** When native-client UI tests run, the shared suite shall capture screenshots and diagnostics, and configured CI jobs shall upload those artifacts. Evidence: `Portal.Client/tests/client.test.js:24-93`, `.github/workflows/build.yaml:96-102,156-162`, `.github/workflows/android.yaml:85-91`.
- [x] **DELIVERY-007** When developers use the documented devcontainer, it shall install the pinned .NET SDK, Node.js, Aspire CLI, and Kubernetes/container tooling. Evidence: `.devcontainer/Dockerfile:1-42`, `.devcontainer/devcontainer.json:1-29`, `global.json:1-5`.
- [ ] **DELIVERY-008** When the main build, Android debug, and native release workflows have all succeeded for the same push to `main`, the publisher shall create one prerelease for that source revision's MinVer version, tagged with the bare version and containing its verified artifacts. Evidence: `.github/workflows/prerelease.yaml`, `.github/scripts/prerelease.mjs`, `.github/scripts/prerelease.test.mjs`.
- [ ] **DELIVERY-009** When a validation run is for a pull request, manual dispatch, or non-release tag, it shall not publish a development release or provide release-write credentials to the build. A stable publisher shall run only for a `vMAJOR.MINOR.PATCH` tag after its required workflows succeed for the same source revision. Evidence: `.github/workflows/build.yaml`, `.github/workflows/prerelease.yaml`, `.github/scripts/release-policy.test.mjs`.
- [ ] **DELIVERY-010** When publishing a development or stable native release, the publisher shall include Linux and Windows artifacts for x86_64 and ARM64 plus the signed Android APK from one native workflow run and attempt, with SHA-256 checksums and commit, run, attempt, architecture, and toolchain provenance. Release notes shall link the required verification runs and disclose that Android arm64 was not tested on a device. Evidence: `.github/workflows/native-release.yaml`, `.github/scripts/prerelease.mjs`, `.github/scripts/prerelease.test.mjs`.
- [ ] **DELIVERY-011** If native release publication is interrupted, previously published releases and their assets shall remain unchanged. The publisher shall resume a draft only for its matching native run and attempt, and shall fail without modifying a conflicting version tag, release channel, draft, or asset. Published prereleases and stable releases shall be immutable. Evidence: `.github/scripts/prerelease.mjs`, `.github/scripts/prerelease.test.mjs`.
- [ ] **DELIVERY-012** When a native release includes Android, it shall publish a signed APK containing `arm64-v8a` and `x86_64` libraries, verify both ABI entries and native library architectures, retain the x86_64 emulator smoke test, and disclose that arm64 has not been device-tested. Signing shall use repository secrets and shall not expose keystore material in logs or artifacts. Evidence: `.github/workflows/native-release.yaml`, `.github/scripts/configure-android-signing.mjs`, `.github/scripts/native-release.test.mjs`, `.github/scripts/android-signing.test.mjs`.
- [ ] **DELIVERY-013** When a successful push to `main` publishes the server container and chart, both shall use the MinVer prerelease version; the image shall also receive a mutable `dev` tag, and neither `latest` nor stable floating tags shall be updated. Evidence: `.github/workflows/build.yaml`, `.github/scripts/release-policy.mjs`, `.github/scripts/release-policy.test.mjs`.
- [ ] **DELIVERY-014** When a stable `vMAJOR.MINOR.PATCH` tag publishes the server container and chart, MinVer shall supply the version without the leading `v`; the image shall receive exact-version, `MAJOR.MINOR`, `MAJOR`, and `latest` tags, and prerelease tags shall not update these stable aliases. Evidence: `.github/workflows/build.yaml`, `.github/scripts/release-policy.mjs`, `.github/scripts/release-policy.test.mjs`.
- [ ] **DELIVERY-015** When a container image is published for either release channel, the referenced OCI tag or tags shall resolve to a manifest supporting both `linux/amd64` and `linux/arm64`. Evidence: `.github/workflows/build.yaml` (multi-RID publish and post-push manifest verification), `.github/scripts/release-workflow.test.mjs`.
- [ ] **DELIVERY-016** When the Helm chart is packaged for either channel, its `version` and `appVersion` shall match the MinVer version, and when `image.tag` is not explicitly overridden, the rendered Deployment shall use `appVersion` as its image tag. Evidence: `.github/workflows/build.yaml`, `chart/templates/deployment.yaml`, `.github/scripts/release-workflow.test.mjs`.
- [ ] **DELIVERY-017** When a stable tag passes the release gate, the publisher shall create an immutable GitHub Release containing the same verified desktop and signed Android artifacts, checksums, and provenance required for a development prerelease. Evidence: `.github/scripts/prerelease.mjs`, `.github/scripts/prerelease.test.mjs`.
- [ ] **DELIVERY-018** When multiple successful main runs qualify for publication, the publisher shall serialize attempts for the same source revision and ref and retain a separate prerelease for each MinVer version, regardless of completion order. If a release for the same version and source revision is already published, a rerun shall leave that release and its assets unchanged. Evidence: `.github/workflows/prerelease.yaml`, `.github/scripts/prerelease.mjs`, `.github/scripts/prerelease.test.mjs`.
- [x] **DELIVERY-019** When Android release signing is configured in a generated Gradle Kotlin script, the adapter shall preserve the generated imports, shall add `import java.util.Properties` only when it is absent, and shall not reference Java types by fully qualified `java.*` names inside the `android {}` block. Evidence: `.github/scripts/configure-android-signing.mjs`, `.github/scripts/android-signing.test.mjs`.
- [ ] **DELIVERY-020** When publishing a development prerelease or stable native release, the publisher shall set the GitHub Release display name to exactly the MinVer semantic version shared by its verified native artifacts, including any prerelease suffix and excluding product labels, a leading `v`, and commit hashes. Evidence: `.github/scripts/prerelease.mjs`, `.github/scripts/prerelease.test.mjs`.
- [ ] **DELIVERY-021** When publishing a native release, the publisher shall name each binary `portal-client-<os>-<architecture>-<version>-b<run-number>.<attempt><extension>`, the checksum file `SHA256SUMS-<version>-b<run-number>.<attempt>`, and the provenance file `provenance-<version>-b<run-number>.<attempt>.json`, using the verified MinVer version and native workflow run number and attempt. Evidence: `.github/scripts/prerelease.mjs`, `.github/scripts/prerelease.test.mjs`.
- [ ] **DELIVERY-022** When publishing a native release, the release notes shall identify the full source commit and link each required verification workflow by name; explain the platform, architecture, build suffix, signing, runtime, and Android testing limitations; describe the client's ability to check and save an address without sign-in or catalog access; and identify the checksum and provenance files with instructions for comparing a download's hash. Evidence: `.github/scripts/prerelease.mjs`, `.github/scripts/prerelease.test.mjs`.
