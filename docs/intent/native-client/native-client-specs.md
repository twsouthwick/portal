# Native Client Specifications

These EARS specifications distinguish observed behavior (`[x]`) from specified
behavior not yet fully verified (`[ ]`). The approved release behavior has
workflow and local-test coverage; hosted builds and signing remain unverified.

- [x] **CLIENT-001** When the native client starts, it shall display the `Portal` heading and `Native client shell` placeholder text. Evidence: `Portal.Client/index.html:8-12`; test: `Portal.Client/tests/client.test.js:24-85`.
- [x] **CLIENT-002** When the Tauri shell creates its primary window, it shall use the configured title, dimensions, frontend URL, and content security policy. Evidence: `Portal.Client/src-tauri/tauri.conf.json:3-35`.
- [x] **CLIENT-003** When the shared client E2E suite runs with a supported adapter, it shall assert the visible placeholder content, capture diagnostics/screenshots, and clean up the launched application. Evidence: `Portal.Client/tests/client.test.js:24-93`.
- [x] **CLIENT-004** When the shared E2E suite runs on Android with the WebView adapter, it shall target the Tauri WebView DOM rather than an unrelated browser target. Evidence: `Portal.Client/tests/adapters/android-webview.js:1-120`; test: `Portal.Client/tests/android-webview.test.js:1-77`.
- [x] **CLIENT-005** When the desktop or Android CI workflow runs, it shall build and smoke-test the configured debug client target. Evidence: `.github/workflows/build.yaml:53-65,138-154`, `.github/workflows/android.yaml:49-87`.
- [ ] **CLIENT-006** When the Android release package is built, it shall be one signed APK containing the `arm64-v8a` and `x86_64` native libraries; CI shall verify both ABI entries and their library architectures. The x86_64 package shall retain emulator smoke coverage, and the release shall not claim arm64 device validation. Evidence: `.github/workflows/native-release.yaml`, `.github/scripts/configure-android-signing.mjs`, `.github/scripts/native-release.test.mjs`, `.github/scripts/android-signing.test.mjs`.
- [ ] **CLIENT-007** When a native release build creates Android or desktop artifacts, the displayed application version shall use the computed MinVer version; the Android `versionCode` shall use the native release workflow run number. Evidence: `.github/workflows/native-release.yaml`, `.github/scripts/native-release.test.mjs`.

### Manual Portal URL onboarding (issue #15)

- [ ] **CLIENT-008** When the user submits a Portal URL, the client shall trim it, assume `https://` when no scheme is given, and normalize it to its origin; it shall reject empty input, unparseable input, user information, a path other than `/`, a query, a fragment, or a scheme other than `https` or permitted `http`. Evidence: `Portal.Client/src-tauri/onboarding/src/origin.rs`.
- [ ] **CLIENT-009** The client shall require `https`; where a debug build enables the `dev-http-loopback` feature, it shall also accept `http` only for `localhost`, `127.0.0.0/8`, or `::1`. Evidence: `Portal.Client/src-tauri/onboarding/src/origin.rs`, `Portal.Client/src-tauri/src/lib.rs`.
- [ ] **CLIENT-010** When the user checks a normalized origin, the Rust host shall send one `GET {origin}/api/manifest` without credentials or cookies, shall not follow redirects, shall validate certificates normally, and shall time out after ten seconds. Evidence: `Portal.Client/src-tauri/onboarding/src/probe.rs`.
- [ ] **CLIENT-011** When the check receives `401` with a `Bearer` challenge, the client shall report that the Portal was found and sign-in is required; when it receives `2xx`, it shall report the Portal as reachable. Evidence: `Portal.Client/src-tauri/onboarding/src/probe.rs`, `Portal.Client/src/main.js`.
- [ ] **CLIENT-012** When the check fails, the client shall report distinct TLS, network, timeout, authentication (`401` without a bearer challenge, `403`, or `407`), redirect, and unexpected-response errors. Evidence: `Portal.Client/src-tauri/onboarding/src/probe.rs`, `Portal.Client/src/main.js`.
- [ ] **CLIENT-013** The client shall save an origin only when the user confirms the most recent successfully checked origin; a new check shall supersede earlier checks, and only a current check's successful result may update the pending origin. The client shall store only the origin, revalidate it when loaded, and not present it as trusted or authenticated. Evidence: `Portal.Client/src-tauri/onboarding/src/pending.rs`, `Portal.Client/src-tauri/onboarding/src/store.rs`, `Portal.Client/src-tauri/src/lib.rs`, `Portal.Client/src/main.js`.

### Authenticated startup and manifest cache (issue #12)

- [ ] **CLIENT-014** When starting sign-in, the client shall fetch OIDC metadata from `GET {portalOrigin}/.well-known/portal-native-oidc` over validated HTTPS without following redirects, validate its required fields, fetch standard OIDC discovery from the declared issuer, and reject a malformed document or issuer mismatch; it shall not accept issuer or endpoint URLs from an authorization callback.
- [ ] **CLIENT-015** When the user signs in to a Portal, the native client shall use the selected separate public OIDC client with the system browser and authorization-code flow with PKCE S256; it shall validate the transaction's state, nonce, issuer, and token validity, and shall not collect passwords or embed a confidential-client secret.
- [ ] **CLIENT-016** When the client requests `GET /api/manifest`, it shall send a valid API access token as a bearer token to the configured Portal origin over validated HTTPS; it shall not use an ID token, Portal cookie, or WebView-managed credential storage.
- [ ] **CLIENT-017** When the client persists a manifest, it shall store only the DTO returned by the authenticated manifest API, together with its ETag, refresh timestamp, and validated issuer-plus-subject account key; it shall not read local site files or Kubernetes resources or cache credentials with the manifest.
- [ ] **CLIENT-018** When startup has a cached manifest for the last authenticated account, the client shall display it immediately as stale or refreshing while requesting an update; on network, provider, or token-refresh failure it shall keep that account's stale manifest visible until a successful refresh replaces it or the user signs out. It shall never display a cache belonging to a different authenticated account.
- [ ] **CLIENT-019** When refreshing with a cached manifest for the authenticated account, the client shall send its ETag in `If-None-Match`; on `200`, it shall validate the complete DTO before atomically replacing the cache, and on `304`, it shall retain the matching DTO and update its successful refresh time. If no cache exists for that account, it shall not send a conditional request and shall not cache a partial or invalid response.
- [ ] **CLIENT-020** When the manifest API returns `401`, the client shall attempt token refresh and retry the request at most once; if refresh or the retry fails, it shall report that sign-in is required without exposing credentials in diagnostics.
- [ ] **CLIENT-021** When the user signs out, the client shall clear that account's cached manifest and credentials; it shall not display the signed-out account's cache to a subsequently authenticated account.
- [ ] **CLIENT-022** When persisting the manifest cache or credentials, the client shall use platform-protected application-private storage for the cache and the platform-protected credential store for credentials; if required protection is unavailable, it shall report the failure and shall not silently fall back to unprotected persistence.
