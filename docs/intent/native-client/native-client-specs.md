# Native Client Specifications

These EARS specifications distinguish observed behavior (`[x]`) from specified
behavior not yet fully verified (`[ ]`). The approved release behavior has
workflow and local-test coverage; hosted builds and signing remain unverified.

- [ ] **CLIENT-001** When the native client starts without a displayed manifest, it shall display the Digital Fortress brand, an `Add your Digital Fortress` heading, a labeled address input, and a connection-check control. Evidence: `Portal.Client/index.html`; test: `Portal.Client/tests/client.test.js`.
- [x] **CLIENT-002** When the Tauri shell creates its primary window, it shall use the configured title, dimensions, frontend URL, and content security policy. Evidence: `Portal.Client/src-tauri/tauri.conf.json:3-35`.
- [ ] **CLIENT-003** When the shared client E2E suite runs with a supported adapter, it shall assert the visible onboarding content, capture diagnostics/screenshots, and clean up the launched application. Evidence: `Portal.Client/tests/client.test.js`.
- [x] **CLIENT-004** When the shared E2E suite runs on Android with the WebView adapter, it shall target the Tauri WebView DOM rather than an unrelated browser target. Evidence: `Portal.Client/tests/adapters/android-webview.js:1-120`; test: `Portal.Client/tests/android-webview.test.js:1-77`.
- [x] **CLIENT-005** When the desktop or Android CI workflow runs, it shall build and smoke-test the configured debug client target. Evidence: `.github/workflows/build.yaml:53-65,138-154`, `.github/workflows/android.yaml:49-87`.
- [ ] **CLIENT-006** When the Android release package is built, it shall be one signed APK containing the `arm64-v8a` and `x86_64` native libraries; CI shall verify both ABI entries and their library architectures. The x86_64 package shall retain emulator smoke coverage, and the release shall not claim arm64 device validation. Evidence: `.github/workflows/native-release.yaml`, `.github/scripts/configure-android-signing.mjs`, `.github/scripts/native-release.test.mjs`, `.github/scripts/android-signing.test.mjs`.
- [ ] **CLIENT-007** When a native release build creates Android or desktop artifacts, the displayed application version shall use the computed MinVer version; the Android `versionCode` shall use the native release workflow run number. Evidence: `.github/workflows/native-release.yaml`, `.github/scripts/native-release.test.mjs`.

### Manual Portal URL onboarding (issue #15)

- [ ] **CLIENT-008** When the user submits a Portal URL, the client shall trim it, assume `https://` when no scheme is given, and normalize it to its origin; it shall reject empty input, unparseable input, user information, a path other than `/`, a query, a fragment, or a scheme other than `https` or permitted `http`. Evidence: `Portal.Client/src-tauri/onboarding/src/origin.rs`.
- [ ] **CLIENT-009** The client shall require `https`; where a debug build enables the `dev-http-loopback` feature, it shall also accept `http` only for `localhost`, `127.0.0.0/8`, or `::1`. Evidence: `Portal.Client/src-tauri/onboarding/src/origin.rs`, `Portal.Client/src-tauri/src/lib.rs`.
- [ ] **CLIENT-010** When the user checks the selected normalized origin, the Rust host shall send one `GET {origin}/api/manifest` without credentials or cookies, shall not follow redirects, shall validate certificates normally, and shall time out after ten seconds. Evidence: `Portal.Client/src-tauri/onboarding/src/probe.rs`.
- [ ] **CLIENT-011** When the check receives `401` with a `Bearer` challenge, the client shall report that the Portal was found and sign-in is required; when it receives `2xx`, it shall report the Portal as reachable. Evidence: `Portal.Client/src-tauri/onboarding/src/probe.rs`, `Portal.Client/src/main.js`.
- [ ] **CLIENT-012** When the check fails, the client shall report distinct TLS, network, timeout, authentication (`401` without a bearer challenge, `403`, or `407`), redirect, and unexpected-response errors. Evidence: `Portal.Client/src-tauri/onboarding/src/probe.rs`, `Portal.Client/src/main.js`.
- [ ] **CLIENT-013** The client shall save an origin only when the user confirms the most recent successfully checked origin; a new check shall supersede earlier checks, and only a current check's successful result may update the pending origin. The client shall store only the origin, revalidate it when loaded, and not present it as trusted or authenticated. Evidence: `Portal.Client/src-tauri/onboarding/src/pending.rs`, `Portal.Client/src-tauri/onboarding/src/store.rs`, `Portal.Client/src-tauri/src/lib.rs`, `Portal.Client/src/main.js`.

### Authenticated startup and manifest cache (issue #12)

- [ ] **CLIENT-014** When starting sign-in, the client shall fetch OIDC metadata from `GET {portalOrigin}/.well-known/portal-native-oidc` over validated HTTPS without following redirects, reject a response body larger than 64 KiB while reading it, validate its required fields, fetch standard OIDC discovery from the declared issuer, and reject a malformed document or issuer mismatch; it shall not accept issuer or endpoint URLs from an authorization callback.
- [ ] **CLIENT-015** When the user signs in to a Portal, the native client shall use the selected separate public OIDC client with the system browser and authorization-code flow with PKCE S256; it shall validate the transaction's state, nonce, issuer, and token validity, and shall not collect passwords or embed a confidential-client secret.
- [ ] **CLIENT-016** When the client requests `GET /api/manifest`, it shall send a valid API access token as a bearer token to the configured Portal origin over validated HTTPS; it shall not use an ID token, Portal cookie, or WebView-managed credential storage.
- [ ] **CLIENT-017** When the client persists a manifest, it shall store only the DTO returned by the authenticated manifest API, together with its ETag, refresh timestamp, and validated issuer-plus-subject account key; it shall not read local site files or Kubernetes resources or cache credentials with the manifest.
- [ ] **CLIENT-018** When startup has a cached manifest for the last authenticated account, the client shall display it immediately as stale or refreshing while requesting an update; on network, provider, or token-refresh failure it shall keep that account's stale manifest visible until a successful refresh replaces it or the user signs out. It shall never display a cache belonging to a different authenticated account.
- [ ] **CLIENT-019** When refreshing with a cached manifest for the authenticated account, the client shall send its ETag in `If-None-Match`; on `200`, it shall validate the complete DTO before atomically replacing the cache, and on `304`, it shall retain the matching DTO and update its successful refresh time. If a validated cache write fails, it shall retain that manifest and ETag in memory for the active account and use them for later refreshes and failure views; it shall clear the in-memory cache on sign-out or account change. If no cache exists for that account, it shall not send a conditional request and shall not cache a partial or invalid response.
- [ ] **CLIENT-020** When the manifest API returns `401`, the client shall attempt token refresh and retry the request at most once; if refresh or the retry fails, it shall report that sign-in is required without exposing credentials in diagnostics.
- [ ] **CLIENT-021** When the user signs out, the client shall clear that account's cached manifest and credentials; it shall not display the signed-out account's cache to a subsequently authenticated account.
- [ ] **CLIENT-022** When persisting the manifest cache or credentials, the client shall use platform-protected application-private storage for the cache and the platform-protected credential store for credentials; if required protection is unavailable, it shall report the failure and shall not silently fall back to unprotected persistence.
- [ ] **CLIENT-047** Before sending a stored refresh token, the client shall require the discovered OIDC issuer to exactly match the issuer bound to the stored account; if they differ, it shall not send the token and shall require a fresh sign-in while retaining that account's cached manifest.

### Optional well-known discovery (issue #16)

- [ ] **CLIENT-023** When the user checks an entered origin, before probing the Portal manifest the Rust host shall send one `GET {origin}/.well-known/digital-fortress/manifest.json` without credentials or cookies, shall not follow redirects, shall validate certificates normally, and shall time out after ten seconds. Evidence and tests: `Portal.Client/src-tauri/onboarding/src/probe.rs`.
- [ ] **CLIENT-024** When discovery returns `200`, the client shall accept a JSON body of at most 8 KiB and use its required `origin` string as the selected origin only if it is an absolute origin valid under CLIENT-008 and CLIENT-009; other fields shall be ignored. Malformed, missing-field, oversized, or invalid-origin documents shall produce an error. Evidence and tests: `Portal.Client/src-tauri/onboarding/src/probe.rs`, `Portal.Client/tests/onboarding.test.js`.
- [ ] **CLIENT-025** When discovery returns `404` or `302`, the client shall use the entered origin for the Portal manifest probe without following a redirect. For any other discovery status or transport failure, it shall report an error rather than silently fall back. Evidence and tests: `Portal.Client/src-tauri/onboarding/src/probe.rs`, `Portal.Client/src/main.js`.
- [ ] **CLIENT-026** When discovery supplies a valid origin, the client shall probe that origin without recursively fetching another discovery document, display the checked origin, and apply CLIENT-013 confirmation and storage only to a successful current check. Evidence: `Portal.Client/src-tauri/onboarding/src/probe.rs`, `Portal.Client/src-tauri/src/lib.rs`, `Portal.Client/src/main.js`; tests: `Portal.Client/src-tauri/onboarding/src/probe.rs`, `Portal.Client/src-tauri/onboarding/src/pending.rs`, `Portal.Client/tests/onboarding.test.js`.

### Onboarding presentation

- [ ] **CLIENT-027** When onboarding is displayed at a viewport width of at least 320 CSS pixels, the client shall present the labeled address input and connection-check control without horizontal scrolling, with keyboard-operable controls and a visible focus indicator. Evidence: `Portal.Client/index.html`, `Portal.Client/src/style.css`; automated viewport and native-platform verification remain pending.
- [ ] **CLIENT-028** When a connection check is pending, succeeds, or fails, the client shall visually distinguish and announce its status; when the address is edited, it shall clear the previous result and hide its save confirmation. Evidence: `Portal.Client/index.html`, `Portal.Client/src/main.js`, `Portal.Client/src/style.css`; test: `Portal.Client/tests/onboarding.test.js`.
- [x] **CLIENT-029** When native onboarding rejects an address or reports a saved-address failure, it shall use the Digital Fortress name while retaining actionable error details. Evidence and tests: `Portal.Client/src-tauri/onboarding/src/origin.rs`, `Portal.Client/src-tauri/onboarding/src/store.rs`, `Portal.Client/src-tauri/onboarding/src/pending.rs`.

### Sign-in, encrypted cache, and site list (issue #12, owner-selected 2026-11-28)

- [ ] **CLIENT-034** When the client signs in on Linux or Windows, it shall use the redirect URI `http://127.0.0.1:49152/oidc-callback`, listen only on `127.0.0.1:49152` for the duration of that sign-in, accept only `GET /oidc-callback`, and report an error when the port is unavailable.
- [ ] **CLIENT-035** When the client signs in on Android, it shall use the redirect URI `digital-fortress:/oidc-callback` and accept that callback only through the registered deep link.
- [ ] **CLIENT-036** When starting sign-in, the client shall open the authorization URL in the system browser with `response_type=code`, PKCE S256, a fresh `state` and nonce, the metadata scopes, and `audience` set to the metadata API audience; it shall reject a callback whose `state` does not match the single pending transaction, keep expiry and cancellation active through token exchange and credential commit, and expire that transaction after five minutes or on cancellation. It shall prevent the user from changing the selected Portal until the sign-in operation finishes.
- [ ] **CLIENT-037** When the token response is received, the client shall validate the ID token signature against the issuer's JWKS and its issuer, audience, expiry, and nonce, and shall use the validated `iss` and `sub` with the Portal origin as the account scope.
- [ ] **CLIENT-038** When persisting a session, the client shall store the origin, issuer, subject, refresh token, and a random 256-bit cache key in one platform credential-store entry; if the store is unavailable, it shall keep the session in memory only and display that sign-in will be required next time. If saving a different account fails, it shall invalidate the previous account's persisted credentials before accepting the new memory-only session; if invalidation fails, it shall reject the account switch and retain the prior active account.
- [ ] **CLIENT-039** When persisting a manifest, the client shall write `manifest-cache/{sha256(origin, iss, sub)}.bin` atomically as XChaCha20-Poly1305 ciphertext under that account's cache key with the file name as associated data, and shall display a cache only if it decrypts and its origin, issuer, and subject match the credential entry.
- [ ] **CLIENT-040** While a manifest is displayed, the client shall show the manifest name and description, a Sign out action, and one status of refreshing, up to date with refresh time, offline or failed with the saved refresh time, or sign-in required.
- [ ] **CLIENT-041** While a manifest is displayed, the client shall render its sites as a responsive card grid grouped under category headings in order of first appearance, listing a site under each of its categories and uncategorized sites under `Other`.
- [ ] **CLIENT-042** When rendering a site card, the client shall show its icon, name, description, and `Private` and `Internal` badges for the corresponding flags, and shall use `bi-globe` unless the icon class matches `bi-` followed by lowercase letters, digits, or hyphens.
- [ ] **CLIENT-043** When the user activates a site card, the client shall show a details view with a Back action, the site's icon, name, badges, and description, and an Open site action only when the site URL is `http` or `https`.
- [ ] **CLIENT-044** When showing usage instructions, the client shall render the Markdown sanitized by DOMPurify, open activated `http` or `https` links in the system browser, and leave other link schemes inert.
- [ ] **CLIENT-045** When showing site apps, the client shall list only apps whose store matches the current platform (`linux` on Linux; `windows` or `microsoft` on Windows; `google` on Android), offer Open for launch URIs other than `javascript`, `data`, `file`, or `vbscript`, and offer Get app only when the store ID is an `https` URL.
- [ ] **CLIENT-046** When the client opens a site, link, or app, it shall do so through the Rust host's system opener and shall not navigate the WebView.

### Version footer

- [x] **CLIENT-030** When the native client starts, its footer shall display the application's packaged version (CLIENT-007).
- [x] **CLIENT-031** When the manifest probe receives a response, the Rust host shall return its `Portal-Version` header value only if it is 1 to 64 characters of ASCII letters, digits, `.`, `+`, or `-`; otherwise it shall treat the website version as absent.
- [x] **CLIENT-032** When a current check finds the Portal and returns a website version, the footer shall display that version; when the address is edited, a newer check starts, or a check fails, the client shall remove the displayed website version.
- [x] **CLIENT-033** When the client starts with a saved origin, the Rust host shall probe that origin's manifest endpoint once under CLIENT-010 without well-known discovery; if the probe finds the Portal and returns a website version, the footer shall display it. A failed probe shall not show an error, change the saved origin, or present the origin as trusted or authenticated.
